# 012 返事の高速化

- 状態：実装中
- 依存：011

## 👤 ユーザーが確認するところ

### 何のための機能か
話し終わってから返事が聞こえるまでが長く、Alexa と比べて待たされる感じがします。いちばん時間のかかっているところから順に縮めます。

### いまの待ち時間（2026-10-23 の測定）
話し終わってから返事が聞こえ始めるまで、おおよそ次の合計で、**道具を使わない質問で約 3.5〜4 秒、買い物リストなどの操作で約 4.5〜6 秒**かかっています。

| 工程 | いま | 理由 |
|---|---|---|
| 話し終わったと判断する | 0.8〜1.2 秒 | 少し黙るのを待って判断する（途中の息つぎで切らないため） |
| 声を文字にする | 約 0.5 秒 | |
| Claude が返事の最初の文を作る | 約 0.9〜1.5 秒（操作は 1.7〜3.3 秒） | 操作のときは「操作する」「結果を見て返事を作る」の2回、Claude に問い合わせている |
| 返事の文を声にする | 約 0.4〜0.9 秒 | 文の音声が全部できあがるまで待ってから送っている |
| 端末で鳴り始める | 約 0.3 秒 | 先頭が欠けないための待ち（2026-10-21 の修正） |

### できるようになること
- **声にするのを待たない**：返事の音声を、できたところから少しずつ受け取って端末に送る。最初の音が出るまでが 0.4〜0.9 秒 → 約 0.2 秒になる（同じ声のまま。試した結果）
- **操作のときの問い合わせを1回にする**：買い物リスト・リマインダー・音量の操作のとき、Claude が「操作」と一緒に「うまくいったら言う言葉」も決める。操作がうまくいけば、その言葉をすぐ読み上げ、2回目の問い合わせをしない。約 1 秒速くなる見込み
  - 「もう入っています」「そのリマインダーはありません」など、思ったとおりにいかなかったときは、今までどおり結果を見て返事を作る（正しい返事を優先する）
- **話し終わりの判断を少し早める**：Google が話し終わりに気づかなかったときの、サーバーの判断を 1.2 秒 → 0.8 秒にする（Google と同じ長さ）
- **待ち時間を記録して比べる**：話し終わってから、端末が鳴り始めるまでの時間を、工程ごとに記録し、レポートで改善前と比べられるようにする

合わせて、**操作で約 1.5〜2.5 秒、質問で約 1 秒**速くなる見込みです（操作で約 3〜3.5 秒、質問で約 2.5〜3 秒）。Alexa ほど速くはなりません。

### 使い方の流れ
1. 「アイリス、買い物リストに牛乳を追加して」
2. 今より早く「牛乳を買い物リストに追加しました」と返ってくる。

### やらないこと（今回は見送り、効果を見てから考える）
- 返事の文が「。」まで書き終わるのを待たずに声にし始めること（さらに 0.2〜0.4 秒ほど速くなるが、作りが複雑になる）
- 声の種類を、速いけれど機械っぽい声に変えること（声の質を優先する。ストリーミングで同じくらい速くなるため）
- 話し終わりの判断の 0.8 秒を、さらに短くすること（「えーと」などの間で切れやすくなる）
- 「考え中」の効果音を鳴らすこと（端末の作りを変える必要がある）

### チャットで決めたこと
| 決めたこと | 理由 |
|---|---|
| 声の種類（Chirp 3 HD）は変えず、ストリーミングで速くする | 試したところ、最初の音までが同じ声で約 0.2 秒になった。速い声（Neural2）は 0.2〜0.4 秒だが、声の質が落ちる |
| 操作がうまくいったときは、Claude が先に決めた言葉をすぐ読み上げる | 2回目の問い合わせ（約 1 秒）を省ける。うまくいかなかったときは今までどおりで、正しさは変わらない |

### 費用
- 変わらない見込み。音声合成の料金は文字数で決まり、ストリーミングでも同じ（実装時に Google の料金表で確かめる）。操作のときは Claude への問い合わせが1回減るので、少し安くなる

  - ふだんの使い方で、返事が速くなったと感じるか。操作のときの返事が不自然になっていないか（感じ方は機械では判定できないため）

## 🤖 実装メモ（Claude 用。ユーザーは読まなくてよい）

### 受け入れ条件
- [ ] AC1：TTS のアダプターに、ストリーミングの合成（`streamingSynthesize`、PCM 24kHz）を足す。`TextToSpeech` に `stream(text, signal)`（PCM の塊を順に返す）を足し、`XiaozhiSink` は塊ごとに Opus にして送る（60ms に満たない端数は次の塊とつなぐ）。最初の文の前の待ち（`startDelayMs`）と先頭の無音はそのまま（自動テスト：偽の TTS が塊で返す。フレームの数とつなぎ目）
- [ ] AC2：ストリーミングが失敗したら、その文はまとめての合成でやり直す（自動テスト）
- [ ] AC3：操作のツール（買い物リスト・リマインダー・音量）の入力に、任意の `reply`（うまくいったら言う、1〜2文の話し言葉）を足す。ツールが「思ったとおり」の結果（追加・削除・登録などが成功し、`existed` などの注意がない）を返し、その回のツール呼び出しがすべて `reply` 付きで成功したら、2回目の LLM の呼び出しをせずに `reply` を読み上げる。そうでなければ今までどおり結果を LLM に返す（自動テスト：偽の LLM で、成功・既にある・エラー・複数ツールの場合）
- [ ] AC4：`reply` で返したときも、履歴は「ツールの呼び出し → ツールの結果 → reply の文」の形で残し、次の発話の文脈が今までと同じになる（自動テスト）
- [ ] AC5：評価（実際の Claude）：`eval:shopping`・`eval:reminder`・`eval:no-hallucination` がすべて合格する。`eval:shopping` の「追加」で、最初の文までの時間の中央値が改善前より 0.5 秒以上短い（コマンド。改善前の値は実装前に測って仕様書に書く）
- [ ] AC6：`localVadEndMs` の既定を 800 にする（`config.example.toml` も）（自動テスト：既存の LocalVad のテストを直す）
- [ ] AC7：待ち時間の記録：`turns` と `listen summary` に、本当の話し終わり（サーバーの判定で最後に声だった時刻。なければ Google の話し終わりの合図）から、端末へ最初の音声を送るまでの時間（`ms_voice_end_to_audio`）を足す。レポートの工程の表に足す（自動テスト）
- [ ] AC8：デプロイ後、実機の会話の `msVoiceEndToAudio` の中央値を、改善前（デプロイ前の記録から推定）と比べて TASKS.md に書く（手動：Claude。fly logs）
- [ ] AC9：返事が速くなったと感じ、操作の返事が不自然でない（手動：ユーザー）

### 設計方針
- TTS：`GoogleTts.stream()` は `streamingSynthesize` に `streamingConfig`（声・PCM・24kHz・`speakingRate`）と `input.text` を書いて閉じ、`audioContent` の塊を返す。`speakingRate` がストリーミングで使えない場合は、仕様書を直して `config` で選べるようにする
- `VoiceSession.speakSentences`：次の文の合成を前の文の再生中に始める今の仕組みは残す。ストリーミングでは「最初の塊が来たら送り始める」
- `reply` の扱いは `Orchestrator`（端末に依存しない部分）に置く。ツールの結果に `ok: true` と `expected: true`（思ったとおり）を持たせ、各ツールで決める（例：`shopping_add` で既にあった場合は `expected: false`）
- プロンプト：`reply` には、ツールの結果を予想した確定の言い方を書かない（「〜しました」は可、件数や残りの品目など結果を見ないと分からないことは書かない）と、ツールの説明とシステムプロンプトに書く
- 測定：`TurnTimings` に `voiceEndAt` を足す。LocalVad に「最後に声だったフレームの時刻」を持たせる

### 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| 速い声（Neural2）に変える | × | まとめての合成で 0.2〜0.4 秒と速いが、声の質が落ちる。ストリーミングで Chirp 3 HD も約 0.2 秒になった |
| ツールの結果から、決まった文（テンプレート）で返事を作る | × | 言い方が機械的になり、「卵とパンも」のような自然な返事ができない。`reply` なら Claude の言い方のまま速くなる |
| thinking をオフにする | × | 考えたことを読み上げてしまう問題がある（CLAUDE.md の消してはいけない設定） |
| LLM の文字が届くそばから TTS に流す | 見送り | さらに 0.2〜0.4 秒速くなるが、文の区切り・読み上げの安全網（isSpeakable）との兼ね合いが複雑。効果を見てから |
