# 仕様書（docs/specs）

機能追加・変更は、相談した結果をここに**1機能＝1ファイル**でまとめてから実装する。

## 👤 ユーザーの読み方
1. 下の「一覧」を上から順に開く。
2. 各仕様書の **「👤 ユーザーが確認するところ」だけ**を読む。「🤖 実装メモ」から下は、Claude が実装のために書いた部分なので読まなくてよい。
3. すべて読んで問題なければ、チャットで「OK」と伝える。直したいところがあれば、その内容をチャットで伝える。
4. OK のあとは、Claude がすべての仕様書を最後まで実装する。仕様書ごとに合意や開始の指示を出す必要はない。

決まっていないことは、仕様書を書く前に Claude がチャットで質問して解消してある。仕様書に「未決」が残っていることはない。

## 🤖 運用ルール（Claude 用）
- ファイル名は `NNN-機能名.md`（3桁の連番）。新規作成は [_template.md](_template.md) をコピーする。
- **仕様書は2つの章に分ける。** 「👤 ユーザーが確認するところ」は、使う人の言葉で短く書く。「🤖 実装メモ」は、実装する Claude にとっての「ゴールと完了条件」なので、曖昧さを残さずに書く。ユーザーが知ったら判断が変わること（費用、データの送り先、使う外部サービス、利用者に見える動作）を実装メモに埋もれさせない。
- **未決事項は、仕様書を書く前にチャットで解消する。** おすすめ案と理由を添えて質問し、すべて決まってから書く。仕様書に「未決事項」の節は作らない。決まった内容は「チャットで決めたこと」と TASKS.md の決定事項ログに書く。
- **仕様書はまとめて書き、まとめて確認を頼む。** 今回作る範囲の仕様書をすべて書いてから、一度だけ確認を頼む。1つずつ合意を求めない。
- 状態は `ドラフト` → `合意済み` → `実装中` → `完了`（やめた場合は `見送り`）。
  **状態の欄には、この5つの語のどれか1つだけを書く。日付・経緯・補足を足さない。**
  - 対象は、仕様書の `- 状態：` の行と、この README の一覧の「状態」の列。
  - 良い例：`- 状態：実装中`　悪い例：`- 状態：実装中（2026-10-03 合意、同日着手）`、`- 状態：ほぼ完了`
  - 状態は、プロジェクト管理のツールが機械的に読む。5つの語と一字でも違うと「不明」として扱われる。
  - 合意した日・着手した日・完了した日などは、TASKS.md の決定事項ログに書く。補足が必要なら、仕様書の本文に書く。
  - 仕様書や一覧を編集すると、hook（`.claude/hooks/spec-status-check.sh`）が状態の書き方を確認し、決まった形でなければ差し戻す。
- **`合意済み` になるまで実装に着手しない。** ユーザーがチャットで合意を伝えたら、Claude が対象の仕様書をすべて `合意済み` にする（ユーザーにファイルを編集させない）。
- **合意後は、依存の順に、すべての仕様書が `完了` になるまで実装を続ける。** 仕様書が1つ終わるたびに、次に進んでよいかを確認しない。
- 受け入れ条件は、テストやコマンドで確認できる形で書く。「いい感じに」「適切に」は書かない。
- 手動確認は最後の手段。ユーザーが行う手動確認は「ユーザーにお願いすること」に理由と一緒に書き、実装がすべて終わってからまとめて頼む。
- 実装中に仕様が変わる場合：
  - 「実装メモ」の中だけで済む変更は、先に仕様書を直してから実装を続ける（確認は不要。最後の報告で伝える）。
  - 「ユーザーが確認するところ」が変わる変更は、実装を止めてチャットで確認する。合意したら仕様書を直して続ける。
- 完了したら、得られた知見を [TECH_NOTES.md](../TECH_NOTES.md) に還元する。
- 公開リポジトリにする場合、仕様書も公開される。個人情報・社内の固有名詞・実際のパスは書かず、例は架空のもので書く。
