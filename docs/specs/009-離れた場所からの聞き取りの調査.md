# 009 離れた場所からの聞き取りの調査

- 状態：完了
- 依存：007

## 👤 ユーザーが確認するところ

### 何のための機能か
キッチンなど離れた場所から話しかけると、「アイリス」には反応するのに、そのあとの言葉が「聞き取れませんでした」になることが多い。原因を数字でつかみ、次の対策を決めるための材料を集めます。

### いま分かっていること
- 音声認識（Google）は、雑音のないきれいな声なら、かなり小さい声（近くで話したときの約 1/16 の大きさ）でも正しく聞き取れた。録音済みの声の大きさを変えて試した
- そのため、「声が小さいから」ではなく、次のどれかが原因の可能性が高い
  - 離れると、声に部屋の響きや生活音（換気扇・水の音など）が混ざって聞き分けにくくなる
  - 「アイリス」のあと、話し始めるまでの待ち時間（いまは 6 秒）に間に合っていない
  - 端末からサーバーへの音声が、途中で途切れている
- いまの記録では、どれなのかを見分けられない

### できるようになること
- 「アイリス」のあとの聞き取りのたびに、次のことを数字で記録する（**音声や話した内容は記録しない**）
  - 声の大きさと、まわりの音（雑音）の大きさ
  - 音声認識が「話し始めた」と判断するまでの時間（判断しなかったかどうか）
  - 音声認識の結果が空だったかどうか
  - 端末からの音声が途切れた時間
- 「聞き取れませんでした」になった回を、上の数字で分けて見られるレポートを出す

### 使い方の流れ
1. 実装とデプロイのあと、ふだんどおり使う。できれば、キッチンなど離れた場所から10回ほど、わざと話しかけてみる（聞き取れなかった回も含めて）。
2. Claude がレポートを見て、原因と対策（次の仕様書）を提案する。

### やらないこと
- 今回は、聞き取りそのものの改善はしない（原因が分かってから、効く対策を選ぶ）
  - 候補：端末のノイズ除去を有効にする、話し始めを待つ時間を延ばす、雑音の多いときの音声認識の設定を変える、など
- 音声を保存して聞き直すこと（音声は保存しない決まりのため）

### チャットで決めたこと
| 決めたこと | 理由 |
|---|---|
| まず原因を数字で調べてから、対策を決める（当て推量で直さない） | 声を大きくするだけの対策は、試した結果、効かない見込みが高いと分かったため |

### ユーザーにお願いすること
- 実装前に準備するもの：なし
- 完成後に手で確認するもの
  - 離れた場所から何度か話しかける（聞き取りの状態を集めるため。Claude には実機に話しかけられないため）

## 🤖 実装メモ（Claude 用。ユーザーは読まなくてよい）

### 受け入れ条件
- [x] AC1：聞き取りごとに、次の値を集計する。音声と認識した文章は含めない（自動テスト：偽の STT と、大きさを決めた PCM で値を確かめる）
  - `audio_ms`：届いた音声の長さ
  - `max_gap_ms`：音声のパケットの間の最大の空き（60ms のフレームが途切れた時間）
  - `ms_to_first_audio`：聞き取りの開始から最初の音声が届くまで（実装中に追加。「アイリス」のあとの音声の通り道が開くまでの遅れを見るため）
  - `noise_rms`：60ms ごとの RMS の 10 パーセンタイル（まわりの音）
  - `speech_rms`：60ms ごとの RMS の 90 パーセンタイル（声）
  - `ms_to_speech_start`：聞き取りの開始から STT の話し始めの合図まで（来なければ null）
  - `finals`：確定した結果の数、`empty_final`：確定した結果がすべて空だったか
  - `no_speech_reason`：`timeout`（話し始めの合図が来ないまま 6 秒）／`empty`（合図は来たが結果が空）
- [x] AC2：上の値を `turns` に保存し（マイグレーションで列を足す）、同じ値を info のログ（`listen summary`）に出す（自動テスト）
- [x] AC3：`npm run report` に「聞き取れなかった回」の節を足す。`no_speech_reason` ごとの回数と、`speech_rms`・`noise_rms`・`ms_to_speech_start`・`max_gap_ms` の中央値を、うまくいった回と並べて出す（自動テスト：固定のデータ）
- [x] AC4：デプロイ後、実機の会話で `listen summary` がログに出る（手動：Claude。`fly logs` で確認）
- [x] AC5：ユーザーが離れた場所から試したあと、レポートとログから原因の見立てと対策をまとめ、次の仕様書の案をチャットで出す（手動：Claude。ユーザーの試用の結果を受け取ってから行う）

### 設計方針
- 集計は `src/core/listen-stats.ts`（端末や通信方式に依存しない）。`VoiceSession.onAudio` で PCM を受け取るたびに 60ms ごとの RMS を足し、受け取った時刻から空きを測る
- STT のイベント（speech_start / final）で `ms_to_speech_start`・`finals`・`empty_final` を記録し、`TurnRecord` に `listen` として載せる
- `turns` の列を足すのは、既存のマイグレーションの仕組みで行う。古い行は null のまま
- ログは数値だけ。認識した文章は今までどおりログに出さない
- 本番のデータベースの読み取りは、ユーザーの許可を得てから（`fly ssh console` の `report`）。許可がなければ `fly logs` の `listen summary` で見る

#### 調査の結果（2026-10-23）
- 実機で6回：聞き取れなかった2回は `timeout`。声の RMS 290・455、まわりの音 52・29 と、声ははっきり届いていたが、5.9 秒のうちに Google の話し始めの合図が来なかった。音声の途切れ（最大 83ms）はなかった
- 聞き取れた4回も、合図は聞き取りの開始から 1967〜3364ms 後だった
- 本物の Google STT に実時間で流すと、合図は声の始まりから 0.6〜1.4 秒後に来る。途中の結果は返ってこない。合図の前に end しても、確定の文章は正しく返る
- 見立て：少し間を置いて話し始めると、合図が来る前に 6 秒が過ぎ、サーバーが声を捨てていた。対策は 011
- 訂正（同日）：6 秒の数え始めは、端末が listen start を送った時点で、ランプが緑になり「ポン」と鳴るのと同じ（xiaozhi v2.5.2 の `HandleStateChangedEvent` → `StartListeningAudio`）。ユーザーは緑になってすぐ話している。したがって「間を置いて話したから」ではなく、離れた声では Google の合図そのものが大きく遅れる・来ない、と見るのが正しい。対策（011：サーバーでも判定し、声を捨てない）は変わらない。実際にいつ話し始めたかは、011 で足した `msToLocalSpeechStart` で確かめる

### 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| サーバーで音量を自動で上げてから STT に渡す（AGC） | × | 録音済みの声を -50dB（RMS 13）まで小さくしても、Google STT は正しく認識した（2026-10-23 に fuji.wav・milk-add.wav で確認）。雑音や響きの割合は音量を上げても変わらない |
| 端末のマイクのゲインを上げる | × | 上と同じ理由で、効く見込みが薄い。ファームウェアの更新も要る |
| 調べるために音声を一時的に保存する | × | 「録音した音声は保存しない」決まりに反する |
