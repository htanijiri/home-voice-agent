# 011 聞き取りの打ち切りの改善

- 状態：完了
- 依存：009

## 👤 ユーザーが確認するところ

### 何のための機能か
離れた場所から話すと、話しているのに「聞き取れませんでした」になることがあります。話している声を捨てずに聞き取るようにします。

### 分かった原因（009 の記録から）
- 2026-10-23 の試しで、聞き取れなかった2回は、どちらも声がはっきり届いていた（まわりの音の6〜15倍の大きさ）
- それでも、音声認識（Google）から「話し始めた」という合図が、待ち時間の 6 秒のうちに来なかった。サーバーはこの合図を待っていて、来なければ、それまでの声を**捨てて**「聞き取れませんでした」と答えていた
- 録音済みの声で試すと、この合図は、話し始めてから 0.6〜1.4 秒遅れて来る。実機では、聞き取れた回でも、合図は緑になってから 2〜3.4 秒後だった
- 6 秒を数え始めるのは、端末のランプが緑になり「ポン」と鳴るのと同じ時点（端末が「聞き取りを始めた」とサーバーに知らせた時点）。緑になってすぐ話しても、離れた場所の声だと、Google が話し始めに気づくのが大きく遅れたり、6 秒のうちに気づかなかったりする
  - （訂正）最初は「緑になってから4〜5秒たって話し始めたから」と説明したが、ユーザーの話（緑になってすぐ話している）と、数え始めの時点をファームウェアで確かめた結果から、合図そのものが遅れる・来ない、と考えるのが正しい
- 合図が来ていなくても、そこまでの声を音声認識に渡し切れば、正しい文章が返ってくることも確かめた

### できるようになること
- 「アイリス」のあと、話し始めるまでの待ち時間（6 秒）のうちに話し始めれば、聞き取れるようになる
  - サーバーでも声の大きさを見て、話し始めたことに自分で気づく（Google の合図を待たない）
  - 話している途中で打ち切らない。話し終わるまで聞く（1回の発話の上限 15 秒は今までどおり）
- 待ち時間が過ぎたときも、それまでに届いた声はすべて音声認識に渡して、結果を待ってから判断する（捨てない）
- 「聞き取れませんでした」は、本当に何も話していなかったときや、言葉として聞き取れなかったときだけになる

### 使い方の流れ
1. キッチンから「アイリス」と呼ぶ。
2. 反応の音を聞いてから、少し間を置いて「買い物リストにクロックムッシュ追加して」と話す。
3. 途中で切れずに聞き取られ、リストに追加される。

### やらないこと
- 話し始めるまでの待ち時間（6 秒）や、1回の発話の上限（15 秒）は変えない（必要なら設定で変えられる）
- 雑音の多い場所での聞き取りの改善（端末のノイズ除去など）。今回の記録では、雑音は原因ではなかった

### チャットで決めたこと
| 決めたこと | 理由 |
|---|---|
| 話し始めの判断を、Google の合図だけに頼らず、サーバーでも声の大きさで行う | Google の合図は遅れて届き、離れた声では 6 秒のうちに来ないこともあるため |
| 待ち時間が過ぎても、それまでの声は捨てずに認識させる | 合図が来ていなくても、正しく認識できることを確かめたため |

### 注意すること
- テレビなど、まわりの話し声を「話し始めた」と判断することが、今より少し増えるかもしれない。その場合は、聞き取りが少し長く続いたあと、聞き取った内容で返事をするか、「聞き取れませんでした」になる

## 🤖 実装メモ（Claude 用。ユーザーは読まなくてよい）

### 受け入れ条件
- [x] AC1：サーバーの声の判定（`LocalVad`）：60ms ごとの RMS が、まわりの音の推定の 3 倍以上かつ 50 以上のフレームが 5 つ（300ms）続いたら「話し始め」、そのあと基準を下回るフレームが 1.2 秒続いたら「話し終わり」とする。まわりの音の推定は、話し始め前のフレームの RMS の移動最小（または低いほうの分位）で追う（自動テスト：決めた PCM で）
- [x] AC2：話し始めの待ち時間（`speechStartTimeoutSeconds`）は、Google の合図かサーバーの判定の早いほうで止める（自動テスト）
- [x] AC3：待ち時間が過ぎても話し始めがなければ、STT を **end** して確定を待つ（abort しない）。確定に文章があれば、それで応答する。空なら「聞き取れませんでした」（`no_speech_reason` は `timeout`）（自動テスト：偽の STT が end のあとに確定を返す）
- [x] AC4：サーバーの判定で話し始めたあと、Google の話し終わりの合図より先にサーバーの「話し終わり」が来たら、STT を end して確定を待つ（自動テスト）
- [x] AC5：追加の聞き取り（返事のあとの 8 秒）でも同じ判定を使う。待ち時間が過ぎて話し始めがなければ、今までどおり何も言わずに待機に戻る（自動テスト）
- [x] AC6：`listen summary` に、サーバーの判定で話し始めた時刻（`msToLocalSpeechStart`）を足し、`turns` にも保存する（自動テスト）
- [x] AC7：本物の Google STT で、声の始まりを「聞き取り開始から 5.5 秒後」（ファイルの頭の無音を含む）にずらした音声を流すと、改善前は「聞き取れませんでした」（Google の合図が 6 秒より後）、改善後は正しく認識される（コマンド：`npm run eval:late-speech`。fuji.wav・milk-add.wav・why.wav で、改善後 3/3。`DELAY_MS` で間を変えられる）
- [x] AC8：離れた場所から、少し間を置いて話しかけて、聞き取られる（手動：ユーザー。2026-10-23 夜、キッチンから9回すべて ok。ユーザーの感想は「それなりに聞き取れてる」）

### 設計方針
- `src/core/local-vad.ts`（端末や通信方式に依存しない）。`ListenStats` と同じく `onAudio` で PCM を受ける
- 判定の値（倍率 3、下限 50、続く長さ 300ms、話し終わりの 1.2 秒）は `config.toml` の `[conversation]` に置く（`localVadRatio`、`localVadMinRms`、`localVadStartMs`、`localVadEndMs`）。009 の記録（聞き取れた遠くの声：雑音 18〜20 に対して声 82〜104）から決めた
- `VoiceSession.startListening`：タイマーの処理を「abort して no_speech」から「end して確定を待つ」に変える。確定を待つ上限は 3 秒（それを過ぎたら abort して no_speech）
- 009 の調査用の記録はそのまま残す（効果を確かめるため）

#### 実装中に変えたこと
- 待ち時間が切れる瞬間に声がし始めていたら（サーバーの判定で、話し始めと判断する手前）、120ms ずつ待ち直す。`eval:late-speech` を 5.5 秒で試したとき、話し始めの判定（300ms 続くこと）が 6 秒に 4ms 間に合わず、「日本」だけで確定してしまったため
- 評価の間を 5 秒から 5.5 秒にした。テストの音声にはファイルの頭に無音があり、5 秒では Google の合図が 6 秒より前（5.5 秒前後）に来て、改善前でも聞き取れてしまうため
- 評価の結果（2026-10-23）：5.0 秒・5.5 秒・5.8 秒のどれも、改善後 3/3。改善前の判定は、5.5 秒と 5.8 秒で 3 つとも「聞き取れませんでした」（Google の合図は 6013〜6586ms）

#### 実機での効果（2026-10-23 夜、キッチンから9回）
- 9回すべて聞き取れた（outcome ok）
- うち5回は、Google の話し始めの合図が最後まで来なかった（`msToSpeechStart` が null）。改善前なら、この5回は「聞き取れませんでした」だった。サーバーの判定で気づき、end して確定を得た
- サーバーが話し始めに気づいたのは、緑になってから 523〜2782ms（1回だけ 5436ms）。ユーザーの「緑になってすぐ話している」と合う
- Google の合図が来た4回は、サーバーの判定の 0.4〜0.6 秒後だった

### 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| 待ち時間を 6 秒から延ばすだけ | × | 合図の遅れのぶん打ち切りが遅くなるだけで、声を捨てる問題は残る。本当に話さないときに待たされる時間も延びる |
| 途中の結果（interim）を話し始めの合図にする | × | chirp_3 では、試した範囲で途中の結果が返ってこなかった |
| 端末のノイズ除去を有効にする | × | 009 の記録では、雑音は原因ではなかった。ファームウェアの更新も要る |
