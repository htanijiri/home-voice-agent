# 016 リビングからの連絡

- 状態：完了
- 依存：008, 013, 014

## 👤 ユーザーが確認するところ

### 何のための機能か
リビングにいる子どもが、外出中の家族に声で連絡できるようにします。「アイリス、パパに連絡して」と言って用件を話すと、確認画面にその文章が届き、スマホに通知が出ます。家族からの返事は、今ある「話す」タブ（014）から送って、アイリスに読み上げてもらいます。

### できるようになること
- **声で連絡する**：「アイリス、パパに連絡して」のあとに用件を話すと、確認画面に届く
  - 用件まで一度に言ってもよい（「アイリス、ママに、今日何時に帰るか聞いて」）
  - 「連絡して」だけのときは、アイリスが「なんて伝える？」と聞き返す。続けて話した言葉を用件として送る
  - 「それだけ」「なんでもない」など、用件がないと答えたら「連絡してほしいそうです」と送る。何も答えなければ送らない
  - 送ったら、アイリスが「パパに送ったよ」のように短く答える
  - 用件は、話した言葉をそのまま送る（Claude が言い換えたり、まとめたりしない）
- **確認画面に「連絡」タブを足す**
  - リビングからの連絡と、「話す」タブから送った文章を、時刻の順に1本に並べて、家族みんなで見る
  - リビングからの連絡には、話した宛先（「パパへ」「お母さんへ」など）と時刻を付ける。宛先を言わなかったら「家族へ」
  - 「話す」タブから送った文章には、送った人（ログインしているアカウントの名前）と、読み上げたかどうかを付ける
  - 画面を開いていれば、その場で表示が更新される（008 と同じ仕組み）
  - 30 日たったものは自動で消す（会話の記録と同じ）
- **スマホに通知する**：リビングから連絡が届くと、通知をオンにした全員のスマホに通知が出る
  - 通知には、宛先と用件の文章が出る（例：「リビングから（パパへ）」「今日何時に帰る？」）。押すと「連絡」タブが開く
  - 通知は、「連絡」タブの「通知を受け取る」ボタンで、スマホ（ブラウザ）ごとにオンにする。もう一度押すとオフ
  - Android の Chrome なら、そのままで通知が届く。iPhone の場合は、確認画面を「ホーム画面に追加」して、そこから開いたときだけ届く
- **宛先は分けない**：「パパ」「ママ」が誰のアカウントかは決めず、誰宛ての連絡も全員の画面に出し、全員に通知する
- **送りすぎを防ぐ**：リビングからの連絡は 1 日 30 件まで。超えたら、アイリスが「今日はもう送れないよ」と答える

### 使い方の流れ
1. 子どもが「アイリス、パパに連絡して」と言う → アイリス「なんて伝える？」
2. 「今日のお迎え、何時？」と話す → アイリス「パパに送ったよ」
3. パパのスマホに「リビングから（パパへ）今日のお迎え、何時？」と通知が出る。押すと「連絡」タブが開く
4. パパが「話す」タブで「5時に行くよ」と送る → リビングでチャイムと「5時に行くよ」の読み上げ
5. 「連絡」タブには、2 の連絡と 4 の返事が並んで見える

### やらないこと
- 読み上げのあと、アイリスが続けて返事を聞き取ること（端末のプログラムの変更が要るため、今回は見送り。返事は「アイリス、パパに連絡して」で送る）
- 「パパ」「ママ」をアカウントに結びつけて、宛先の人にだけ通知すること
- 誰が話したかを聞き分けること（差出人はいつも「リビングから」）
- 声そのものを送ること（今までどおり、録音は保存しない。送るのは文字だけ）
- 連絡を画面から消すこと（30 日で自動で消える）
- メールや LINE への通知

### 014 から変わること
- 014 では「話す」タブから送った文章を保存しないと決めたが、この仕様からは「連絡」タブに並べるため、**30 日間保存する**（リビングからの連絡と同じ）

### チャットで決めたこと
| 決めたこと | 理由 |
|---|---|
| 読み上げのあとに返事を聞き取る機能は作らない。返事は「アイリス、パパに連絡して」で送る | 端末のプログラムの変更と USB での書き込みが要るため（ユーザーの判断） |
| 通知は Web Push（ブラウザのプッシュ通知） | 家族のスマホが Android で、無料・外部のアカウントなしで届くため |
| 連絡は家族みんなで1本のやり取りとして見て、30 日保存する。「話す」タブから送った文章も並べる | やり取りの流れが分かるように |
| 宛先の呼び名とアカウントは結びつけず、全員の画面に出して全員に通知する | 家族で共有できれば十分（ユーザーの判断） |
| 「連絡して」だけのときは聞き返す | 「パパに連絡して」と言ってから用件を話す、という使い方のため（ユーザーの想定） |

### 費用・データの送り先
- 費用：ふだんの会話 1 回ぶんと同じ（音声認識・Claude・読み上げ）。通知は無料
- データの送り先：通知は、Google のプッシュ通知の仕組み（Android の Chrome が使うもの）を通ってスマホに届く。中身は暗号化されて送られ、途中の Google には読めない。用件の文章はサーバーのデータベースに 30 日保存する

### ユーザーにお願いすること
- 実装前に準備するもの：なし（通知用の鍵は、サーバーが初めて起動したときに自分で作る）
- 完成後に手で確認するもの
  - スマホ（Android の Chrome）で「連絡」タブの「通知を受け取る」を押して、許可する（通知の許可は、スマホを持つ人にしか押せないため）
  - リビングで「アイリス、パパに連絡して」→ 用件を話す → スマホに通知が届き、押すと「連絡」タブが開く（実機の声と、スマホの通知は機械では確かめられないため）

## 🤖 実装メモ（Claude 用。ユーザーは読まなくてよい）

### 受け入れ条件
- [x] AC1：ツール `send_family_message`（入力：`to`（話した宛先。省略可）、`text`（用件、100 文字まで）、`reply`）。呼ばれたら `family_messages` に保存し、変更通知（SSE）と Web Push を送る。reply 付き（012 の仕組み）で、成功したら2回目の LLM を呼ばない（自動テスト）
- [x] AC2：1 日（Asia/Tokyo）の件数が上限（`[family] maxMessagesPerDay = 30`）に達していたら、保存も通知もせず、エラーとして返す（LLM が「今日はもう送れない」と答える）（自動テスト）
- [x] AC3：`/api/announce` で送った文章を `family_messages` に保存する（種類 `announce`、送った人のメール、結果 sent/queued/offline/busy）。待ち行列から読み上げた・あきらめたときは結果を更新する（自動テスト）
- [x] AC4：`GET /api/messages`（ログインが必要）で、新しい順に最大 100 件返す。30 日より古いものは、毎日の削除の処理（retention）で消す（自動テスト）
- [x] AC5：`POST /api/push/subscribe`・`/api/push/unsubscribe`（ログイン・CSRF が必要）で購読を保存・削除する。送った先が 404・410 を返した購読は消す（自動テスト：偽の送り先）
- [x] AC6：VAPID の鍵は、初めて起動したときに作って kv に保存し、以後はそれを使う。公開鍵は画面に渡す。秘密鍵はログ・画面に出さない（自動テスト）
- [x] AC7：Web Push の暗号化（RFC 8291 aes128gcm）と VAPID（RFC 8292）の結果を、RFC 8291 の付録の例で確かめる。ライブラリを使う場合はその単体の確認でよい（自動テスト）
- [x] AC8：画面に「連絡」タブ。並び・宛先・時刻・送った人・結果を出す。「通知を受け取る」ボタン（オン・オフ）。SSE で読み直す。Service Worker（`/sw.js`）が通知を出し、押すと `/#messages` を開く。スマホの幅で崩れない（手動：Claude。`npm run web-preview` を内蔵ブラウザのモバイル表示で）
- [x] AC9：評価（実際の Claude）`npm run eval:message`：「パパに連絡して」→ ツールを呼ばずに聞き返す、続けて用件 → 用件のとおりの `text` で送る。「ママに、今日何時に帰るか聞いて」→ 1回で送り、`to` が「ママ」。「お母さんに連絡して」→「それだけ」→「連絡してほしいそうです」で送る。続けての聞き取りで聞き返しへの答えを、話しかけでない声として無視しない（各 5/5）。既存の評価もすべて合格（コマンド）
- [x] AC10：用件の文章をログに出さない（ログには文字数だけ）（手動：Claude。コードと `fly logs` で確認）
- [ ] AC11：実機で、声の連絡がスマホに通知され、押すと「連絡」タブが開く（手動：ユーザー）

### 設計方針
- テーブル `family_messages`（id, kind `voice`/`announce`, to_label, text, sender_email, status, created_at）。マイグレーション 10。購読は `push_subscriptions`（endpoint 主キー, p256dh, auth, email, created_at）
- `src/db/messages-repo.ts`（保存・一覧・1日の件数・古いものの削除・onChange）、`src/app/push.ts`（購読・送信。送る処理はアダプターに分け、テストでは偽物）
- ツールは `src/core/tools/messages.ts`。保存と通知は `ToolContext` に足した口（`sendFamilyMessage`）経由で行い、core から DB や Web Push を直接呼ばない
- 聞き返しのあとの用件は、続けての聞き取り（013）で受ける。`prompts/system.md` に「直前に『なんて伝える？』と聞いたら、次の発話は用件として扱い、無視しない」を足す
- Web Push の送信は `web-push`（npm）を使うか、`jose` と `node:crypto` で書く。依存を増やさずに済むなら後者
- 画面：`page.ts` にタブを足す。`/sw.js` と `manifest.webmanifest`（iPhone のホーム画面用）を出す
- 設定：`[family] maxMessagesPerDay = 30`、`messageMaxChars = 100`（`config.example.toml` にも）

#### 実装中に変えたこと・測った値
- 保存と通知の口は、`ToolContext` ではなく、ツールを作るときに渡す `FamilyMessenger`（`messageTools(messenger, maxChars)`）にした。買い物リストのツールがリポジトリを受け取るのと同じ形
- 送った人の名前は、Google のログインに `profile` を足して ID トークンの `name` を使う（`web_sessions.name`）。前からのログインで名前がなければ、メールの @ より前を出す
- Web Push は `web-push` を使わず、`node:crypto` と `jose` で書いた（`src/adapters/web-push.ts`）。RFC 8291 付録 A の例と一致することを確認
- 購読の送り先は、ブラウザのプッシュの仕組みのホスト（Google・Mozilla・Apple・Microsoft）だけを受け付ける（サーバーから任意の URL に通信させないため）。確認画面に入れなくなった人の購読は、毎日 4:00 に消す
- 通知は返事を待たずに送る（返事の速さを変えないため）
- 画面：`/sw.js`・`/manifest.webmanifest`・`/icon-192.png` はログインなしで出す（`src/web/pwa.ts`。秘密の情報は入れない）。通知を押したとき、開いている画面があれば Service Worker から `postMessage` で「連絡」タブに切り替える
- 評価（2026-10-27）：既存の `eval:end`・`eval:no-hallucination`・`eval:shopping`・`eval:reminder` もすべて合格。`eval:message` は 4 項目とも 5/5（聞き返しは毎回「なんて伝える？」、用件は「今日のお迎え、何時？」「今日何時に帰る？」のとおり）

### 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| 読み上げのあと、続けて返事を聞き取る | × | xiaozhi v2.5.2 の notify は再生後に待機に戻るだけで、サーバーから聞き取りを始めさせる命令がない。ファームウェアの変更と USB での書き込みが要る（ユーザーの判断で見送り） |
| Claude が用件を短くまとめて送る | × | 子どもの言葉のまま届けたい。言い換えで意味が変わるおそれがある |
| メール・LINE で通知 | × | 送信用のアカウントや外部サービスの登録が要る。Web Push なら追加の準備なし |
| VAPID の鍵を Fly.io の秘密情報に入れる | × | ユーザーの作業が増える。サーバーの DB（kv）に置けば、公開リポジトリにも入らない |
