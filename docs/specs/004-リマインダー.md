# 004 リマインダー

- 状態：完了
- 依存：003

## 👤 ユーザーが確認するところ

### 何のための機能か
Alexa のもう1つの主な用途のリマインダーを、声で登録でき、時刻どおりに読み上げてくれるようにします。

### できるようになること
- **登録**
  - 「明日の朝8時にゴミ出しを教えて」で登録し、「10月21日（水）午前8時に『ゴミ出し』をお知らせします」と日時を言い直して確かめる
  - 「明日」「来週の金曜」「3時間後」「毎週月曜」などを、日本時間で解釈する
- **はっきりしないときは聞き返す**
  - 時刻がない（「金曜にゴミ出し」）→「何時にお知らせしますか？」
  - 午前か午後か分からない（「8時に」で、どちらもこれから先の時刻）→「午前8時ですか、午後8時ですか？」
  - 過去の日時になる →「その時刻はもう過ぎています」と伝えて聞き直す
- **繰り返し**：次の繰り返しを登録できる
  - 毎日
  - 平日
  - 毎週◯曜日（複数の曜日も可）
  - 毎月◯日
  - 毎月第◯◯曜日（例：第2・第4水曜。ゴミの日によくある形）
- **確認**：「リマインダーを教えて」で、これから先の予定を近い順に5件読み上げる
- **変更**：「ゴミ出しのリマインダーを7時にして」
- **削除**
  - 「ゴミ出しのリマインダーを消して」
  - 繰り返しのものは、「次の1回だけ休む」か「全部消す」かを聞く
- **時刻になったら**
  - チャイムのあとに「ゴミ出しの時間です」と読み上げ、画面にも字幕を出す
  - **5分以内に反応（ボタンか呼びかけ）がなければ、もう1回だけ読み上げる**（最大2回）
    - （2026-10-27 変更、spec 015）5分後ではなく、読み上げが終わってから約 10 秒のうちに反応がなければ、すぐもう1回だけ読み上げる
  - 同じ時刻に複数あるときは、まとめて1回で読み上げる
  - 会話の途中に時刻が来たら、会話が終わってから読み上げる
  - 夜間（22:00〜7:00）は小さめの音量で読み上げる
- **読み上げを止める**：読み上げ中にボタンを押すと止まり、2回目も鳴らない
- **端末がつながっていなかったとき**（Wi-Fi が切れた、停電など）
  - 遅れが2時間以内なら、つながったときに「遅れてお知らせします。ゴミ出しの時間でした」と読み上げる
  - 2時間より古いものは読み上げず、次に話しかけたときに「お知らせできなかったリマインダーがあります。ゴミ出し（午前8時）」と伝える
- **消えない・重ならない**
  - サーバーや端末を再起動しても、リマインダーは消えない
  - 同じ回を重ねて通知しない（上の「もう1回」を除く）

### 使い方の流れ
1. 「アイリス、毎週月曜と木曜の朝7時半に燃えるゴミを教えて」
2. 「毎週月曜日と木曜日の午前7時30分に『燃えるゴミ』をお知らせします」
3. 月曜の 7:30 に、チャイムと「燃えるゴミの時間です」。聞こえたらボタンを押す（押さなければ 7:35 にもう1回）。

### やらないこと
- 「家に帰ったら」のような場所での通知
- スマホへの通知（LINE やプッシュ通知）
- 家族ごとのリマインダー（全員で共有する1つの一覧にする）
- 祝日を考えた繰り返し（祝日のゴミ収集の休みなど）

### チャットで決めたこと
| 決めたこと | 理由 |
|---|---|
| 反応がなければ5分後にもう1回読み上げる（最大2回） | 聞き逃しを減らしつつ、繰り返しすぎない |
| 端末がつながっていなかった場合、遅れが2時間以内なら復帰後に読み上げる。それより古いものは次の会話で伝える | 遅れても役に立つものは伝え、古い通知が夜中に鳴るのは避ける |
| 夜間は小さめの音量で読み上げる | 夜間の生活音への配慮 |

### ユーザーにお願いすること
- 実装前に準備するもの：なし
- 完成後に手で確認するもの
  - チャイムと読み上げが、ほかの部屋や家事の最中にも気づける大きさか（聞こえ方は家ごとに違い、機械では判定できないため）

## 🤖 実装メモ（Claude 用。ユーザーは読まなくてよい）

### 受け入れ条件
- [ ] AC1：日時の解釈と検証
  - LLM が出した「日付・時刻・繰り返しの指定」を、サーバーが Asia/Tokyo で検証して次の通知時刻を計算する
  - 時刻がない・過去になる・午前か午後か曖昧なときは、エラーを返して聞き返させる
  - （自動テスト：基準時刻を固定して、「明日」「来週金曜」「3時間後」「月末」「第2・第4水曜」「うるう年の2月29日」「毎月31日（31日がない月）」などを確かめる）
- [ ] AC2：繰り返しの次回の計算（毎日・平日・毎週の複数の曜日・毎月◯日・毎月第◯◯曜日）（自動テスト）
- [ ] AC3：スケジューラーが、保存された次の通知時刻をもとに通知を出す
  - サーバーを再起動しても、通知を失わない
  - 同じ回を2回出さない（自動テスト：偽の時計。各回の通知に冪等なキー（リマインダーの ID と予定の時刻）を付け、二重送信を拒む）
- [ ] AC4：MQTT＋UDP の通信方式
  - OTA の応答で端末を MQTT＋UDP に切り替える
  - 会話（001・002 の機能）が WebSocket のときと同じく動く
  - （自動テスト：偽の端末で MQTT＋UDP の hello、AES-CTR で暗号化した音声の往復、listen と tts の流れを確認）
- [ ] AC5：通知
  - 時刻になると、端末に `notify` を送る（チャイムと TTS の Ogg Opus の URL。URL は1回だけ使える短命の署名付き）
  - 5分以内に反応がなければ1回だけ再送する
  - 反応（端末の hello・listen detect・ボタンでの abort）があれば再送しない
  - （自動テスト：偽の時計と偽の端末）
- [ ] AC6：会話中は通知を待ち、待機に戻ったら送る（自動テスト）
- [ ] AC7：端末がつながっていないときの扱い
  - 遅れが2時間以内なら、再接続したときに「遅れてお知らせします」を付けて送る
  - 2時間より古いものは「未通知」として保存し、次の会話の最初に伝えたら「伝達済み」にする
  - （自動テスト）
- [ ] AC8：会話の評価で、「明日の午前8時にゴミ出しを教えて」→ 翌日 08:00 JST のリマインダーが1件保存される。「金曜にゴミ出し」→ 時刻を聞き返し、保存しない（コマンド：評価スクリプト。各5回）
- [ ] AC9：実機で、2分後のリマインダーを登録すると、時刻どおりに読み上げられる。サーバーを再起動したあとも、別のリマインダーが1回だけ読み上げられる（手動：Claude。端末のログとサーバーのログで確認）

### 設計方針
- テーブル
  - `reminders`：id、household_id、title、schedule（JSON：一回限りの日時、または繰り返しの規則）、next_fire_at（UTC）、status（`active` / `done` / `deleted`）、skip_next
  - `reminder_deliveries`：id、reminder_id、scheduled_at、attempt、state（`pending` / `sent` / `acknowledged` / `missed` / `told`）、sent_at、ack_at。（reminder_id、scheduled_at、attempt）で一意にする
- 日時の計算は Temporal のポリフィル（`@js-temporal/polyfill`）か、`date-fns-tz` で書く。LLM には相対表現をそのまま解かせず、構造化した値（日付・時刻・繰り返しの規則）を出させ、サーバーが計算する
- システムプロンプトには、現在の日時（Asia/Tokyo、曜日つき）を毎回入れる
- スケジューラー
  - プロセス内で、10秒ごとに `next_fire_at <= now` のものを処理する
  - 起動時には、取りこぼしたものを「遅れ」として、2時間ルールで処理する
  - 運用は1台のマシンなので、分散ロックは持たない
- MQTT＋UDP
  - サーバーのプロセス内に MQTT ブローカー（aedes）を持つ。端末の認証は OTA で返す MQTT のユーザー名・パスワード（端末用トークン）で行う
  - UDP は `node:dgram` で受け、セッションごとの AES-CTR の鍵とノンスを hello の応答で渡す
  - 開発中は TLS なし（LAN 内）。運用では TLS を使う（→ 006）
- 通知の音声
  - TTS で Ogg Opus を作り、メモリ上のキャッシュに置く（短命の URL、5分で破棄）
  - チャイムは Ogg Opus のファイルとして同梱する（自作するか、自由に使えるライセンスの音源）
- 「未通知」の伝達は、次のセッションの最初の応答の前に、システムからのメッセージとして LLM に渡す


#### 実装中に変えたこと
- 通知の記録は1回の予定につき1行（`reminder_id` と `scheduled_at` で一意）とし、読み上げた回数を `attempts` に持つ。
- チャイムは、端末が notify の前に鳴らす内蔵の通知音を使う（音源のファイルは持たない）。
- 「毎月◯日」で、その月にない日（31日など）は、その月の最終日に知らせる。
- 音声合成に失敗したときは、notify の代わりに alert（画面の表示と通知音）で知らせる。
- 端末は MQTT のトピックを購読しないので、ブローカー（aedes）から接続ごとに直接メッセージを届ける。

### 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| 時刻の計算を LLM に任せる | × | BRIEF のとおり、時刻の管理は LLM に任せない |
| node-cron などの外部のスケジューラー | × | 再起動で状態を失う。データベースの next_fire_at を見る方式にする |
| WebSocket のまま、端末に定期的に接続させる | × | ファームウェアの大きな改造が必要。公式の MQTT＋UDP を使う |

- コマンド：`npm run eval:reminder`
