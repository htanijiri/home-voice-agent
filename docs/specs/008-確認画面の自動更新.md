# 008 確認画面の自動更新

- 状態：実装中
- 依存：005

## 👤 ユーザーが確認するところ

### 何のための機能か
買い物中に家族が「アイリス、買い物リストに〇〇を追加して」と頼んでも、スマホの確認画面は再読み込みしないと変わりません。開いている画面に、変更がすぐ映るようにします。

### できるようになること
- 確認画面を開いている間、買い物リストが変わると、**1〜2秒で自動的に画面が新しくなる**
  - アイリスに頼んだ追加・「買った」・削除
  - 家族が別のスマホで操作した変更
- **リマインダーのタブも同じように自動で新しくなる**（声で登録・変更・削除したもの、お知らせが済んで次の予定に進んだもの）
- スマホを閉じていた（画面を消していた、別のアプリを使っていた）あとで確認画面に戻ったときも、すぐに最新の内容になる
- 電波が悪くて一時的につながらなくなっても、つながり直したときに最新の内容になる

### 使い方の流れ
1. お店でスマホの確認画面（買い物リスト）を開いておく。
2. 家で家族が「アイリス、買い物リストに牛乳を追加して」と頼む。
3. 再読み込みしなくても、スマホの一覧に「牛乳」が出る。

### やらないこと
- スマホへのプッシュ通知（画面を開いていないときに知らせること）
- 何が変わったかの強調表示や通知音（一覧が新しくなるだけ）
- 「その他」のタブ（端末・会話の記録・利用量）の自動更新

### チャットで決めたこと
| 決めたこと | 理由 |
|---|---|
| 画面を開いている間はサーバーとつなぎっぱなしにし、変更があったらサーバーから知らせる（定期的に確かめに行く方式にはしない） | 変更がすぐ映る。変更がないときはほとんど通信しない |
| 買い物リストに加えて、リマインダーのタブも自動で新しくする | 声で登録したリマインダーも、同じ理由で画面に映らないため。仕組みは同じで、手間がほとんど増えない |

### ユーザーにお願いすること
- 実装前に準備するもの：なし
- 完成後に手で確認するもの
  - スマホで確認画面を開いたまま、アイリスに買い物リストの追加を頼み、再読み込みなしで一覧に出る（実機の端末とスマホの組み合わせは、Claude には試せないため）

## 🤖 実装メモ（Claude 用。ユーザーは読まなくてよい）

### 受け入れ条件
- [ ] AC1：買い物リスト・リマインダーのリポジトリで内容が変わる操作（追加・修正・買った・戻す・削除・全部消す、リマインダーの登録・変更・削除・次だけ休む・お知らせによる次の予定への進行）のたびに、その家庭の変更の通知が出る。読むだけの操作では出ない（自動テスト）
- [ ] AC2：`GET /api/events` が Server-Sent Events で、変更の種類（`shopping` / `reminders`）を送る（自動テスト：実際に HTTP でつなぎ、音声のツールと同じリポジトリで追加すると届く）
- [ ] AC3：`/api/events` もログインが必要（未ログインは 401）（自動テスト）
- [ ] AC4：つながっている間、25 秒ごとに空のコメント（ハートビート）を送る。切断したら購読を外す（自動テスト：切断後に購読数が 0 に戻る）
- [ ] AC5：画面は、変更の通知を受けたら、表示中のタブが該当するときだけ一覧を読み直す。短い間に続いた通知はまとめて1回にする。つながり直したとき・画面が表示に戻ったとき（visibilitychange）にも読み直す（手動：Claude。内蔵ブラウザで画面を開き、API から追加して再読み込みなしで表示が変わることを確かめる）
- [ ] AC6：Fly.io で、SSE がプロキシを通って届く（手動：Claude。デプロイ後に `curl -N` で、ログインのセッションなしに 401、偽の端末や画面の操作で通知が届くことを確かめる。ログインが要るため、通知の受信は内蔵ブラウザまたはテスト用のセッションで確かめる）
- [ ] AC7：スマホで開いたまま、アイリスに追加を頼むと、再読み込みなしで一覧に出る（手動：ユーザー）

### 設計方針
- `src/app/change-feed.ts`：家庭ごとの変更の通知（`notify(householdId, topic)`、`subscribe(fn) → 解除`）。プロセスは1つ（Fly.io のマシン1台）なので、メモリ上の購読で足りる
- `ShoppingRepo` / `RemindersRepo` は、コンストラクタで変更時のコールバック（省略可）を受け取り、書き込みの操作の最後に呼ぶ。音声のツール・確認画面・スケジューラーのどこから変えても通知が出るよう、リポジトリで通知する
  - リマインダーは `takeDue`（次の予定へ進む）も通知する。配信の状態だけの変更（`markSent` / `setState`）は一覧の表示が変わらないので通知しない
  - `purge`（古い「買った」の削除）は「最近買ったもの」の表示範囲外なので通知しない
- `GET /api/events`：`reply.hijack()` して `text/event-stream` を書く。`Cache-Control: no-store`、最初に `retry: 3000` を送る。ハートビートは 25 秒（Fly のプロキシのアイドル切断を避ける）
- 画面：`EventSource('/api/events')`。`shopping` / `reminders` のイベントで、表示中のタブなら 300ms まとめてから読み直す。`open`（初回を除く）と `visibilitychange`（visible）でも読み直す。入力中のフォーム（追加・リマインダーの編集）は一覧と別の要素なので、読み直しても消えない

### 検討した案と不採用の理由
| 案 | 採用 | 理由 |
|---|---|---|
| 数秒ごとに読み直す（ポーリング） | × | 遅れが出るうえ、変更がなくても通信し続ける。SSE がつながらない環境は今のところない |
| WebSocket | × | 画面からサーバーへ送るものがなく、片方向の SSE で足りる。EventSource は再接続を自分でしてくれる |
| 変更の中身（追加された品物）を送って画面で差し込む | × | 一覧を読み直すほうが単純で、表示がずれない。一覧は小さい |

### 検証方法
- 自動テスト：`npm test`（変更の通知、`/api/events` の配信・認証・切断）
- 手動確認（Claude）：`npm run web-preview` を内蔵ブラウザで開き、別の経路から追加して自動で表示が変わること。デプロイ後に Fly.io で SSE が届くこと
- 手動確認（ユーザー）：実機の端末とスマホで、声の追加が画面に出ること
