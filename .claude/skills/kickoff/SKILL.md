# キックオフ：BRIEF から仕様書を作り、合意をもらって実装する

チャットで相談してまとめた計画書 `brief/BRIEF.md` を読み、このプロジェクトを次の順で進める。

1. 決まっていないことをチャットで質問し、すべて決める
2. ドキュメントと、今回作る範囲のすべての仕様書を書く
3. ユーザーに一度だけ確認を頼む
4. 合意をもらったら、すべての仕様書を最後まで実装する

**合意をもらうまでは実装しない。** ユーザーが指示を出すのは、質問への回答と、最後の「OK」だけになるようにする。

## 1. 事前確認
- `brief/BRIEF.md` がなければ、「計画書を brief/BRIEF.md に置いてから、もう一度 /kickoff してください」と伝えて終了する。
- `brief/` にほかの資料（画像、ワイヤーフレーム、チャットのログなど）があれば、それも読む。
- **すでにキックオフ済みか確認する。** `docs/specs/` に `000-` 以降の仕様書がある、または CLAUDE.md の冒頭の `<!-- -->` が埋まっている場合は、上書きせずにユーザーに確認する（「やり直す」「BRIEF の更新分だけ反映する」「やめる」のどれにするか）。

## 2. BRIEF を読んで整理する
BRIEF を最後まで読み、次の点を整理する。
- 何を作るか、誰がどの端末で使うか
- 解決したい課題と、あえてやらないこと
- 機能の一覧と、今回作る範囲（あとに回すものはどれか）
- 制約（公開リポジトリにするか、データの扱い、予算、対象端末、期限など）
- 技術スタック（決まっているか、候補だけか、未定か）
- 決まっていないこと・曖昧なこと

## 3. 未決事項をチャットで解消する
**決まっていないことは、ファイルに書き残さず、ここでチャットで質問してすべて決める。** 未決事項がなくなるまで、4 に進まない。

- 質問は AskUserQuestion ツールで行う（使えない場合は、番号を付けてチャットに書く）。
- 各質問に選択肢を付け、おすすめ案を先頭に置いて理由を一言添える。ユーザーが選ぶだけで答えられるようにする。
- 関連する質問はまとめて一度に聞く。答えから新しい疑問が出たら、続けて質問する。
- 「おまかせ」と言われたら、おすすめ案で決める（決定事項ログに「おまかせ」と書く）。

質問すること（ユーザーが知ったら判断が変わること）：
- 今回作る範囲、機能の動き、画面や操作の流れで BRIEF から読み取れないこと
- 技術スタックが未定・候補だけの場合の選択
- 費用がかかるもの、データの送り先、使う外部サービス
- デプロイ先、公開範囲
- ユーザーにしかできない準備（アカウント、API キーなど）が必要になる選択

質問しないこと：
- BRIEF から読み取れること
- ユーザーが知っても判断が変わらない実装の細部（ファイル構成、ライブラリの細かい選択、命名など）。Claude が決めて、仕様書の「実装メモ」に理由を書く。

## 4. ファイルを作る・埋める
各ファイルの `<!-- -->` は、埋めたら消す。まだ埋められない部分（コマンド、デプロイなど）は `<!-- -->` を残しておく。

| ファイル | 書くこと |
|---|---|
| `CLAUDE.md` | 冒頭の一行の概要、「絶対に守ること」に追記するプロジェクト固有の制約、「技術スタック・設計方針」。**テンプレートにもともとある共通ルール（進め方、ドキュメントの書き分け、作業ジャーナルなど）は消さない・書き換えない** |
| `README.md` | 概要、設計の前提、主な機能 |
| `TASKS.md` | 決定事項ログ（3 で決めたこと）、フェーズ分け、各タスクに対応する仕様書の番号 |
| `docs/HISTORY.md` | 「このアプリは何か」「出発点となった要望」（BRIEF の要点）。BRIEF や 3 で決まった設計判断は「主要な設計判断」にも書く |
| `docs/TECH_NOTES.md` | 「技術選定」に、選んだ技術と理由を書く |
| `docs/specs/NNN-機能名.md` | **今回作る範囲の機能すべて**を、1機能＝1ファイルで作る（MVP だけで止めない。BRIEF で「あとで」「将来」とされたものは作らず、「やらないこと」に書く）。`_template.md` をコピーして書き、状態は `ドラフト` にする。基盤づくり（開発環境、デプロイ先、検証の方法）が必要なら `000-` にする |
| `docs/specs/README.md` | 一覧表に、作った仕様書を読む順（＝実装する順）で追加する |

仕様書を書くときの注意：
- **「👤 ユーザーが確認するところ」と「🤖 実装メモ」を分けて書く。** 前者は、ファイル名・関数名・専門用語を使わず、使う人の言葉で短く書く。ユーザーはここしか読まない。
- ユーザーが知ったら判断が変わること（費用、データの送り先、使う外部サービス、利用者に見える動作）は、実装メモに埋もれさせず、「ユーザーが確認するところ」に書く。
- 3 で決めたことは、関係する仕様書の「チャットで決めたこと」に書く。
- 受け入れ条件は、コマンドや手順で確認できる形で書く（「いい感じに」「適切に」とは書かない）。
- 受け入れ条件の確認は、まず自動テストやコマンドで行う方法を考える。ユーザーの手動確認を残す場合は、「ユーザーにお願いすること」に、確かめられない理由と一緒に書く。
- 書いている途中で未決事項が見つかったら、仕様書に書き残さず、3 に戻って質問する。

全体の注意：
- `brief/` 以外のファイルは Git 管理され、公開される可能性がある。BRIEF に出てくる人名・社内の固有名詞・実際のパスやアカウント情報は、一般的な言い方に直して書く。
- `brief/BRIEF.md` 自体は書き換えない。

## 5. 合意の前にやらないこと
- 実装に着手すること（package.json などのコードやひな形を作ることも含む）
- 仕様書の状態を `合意済み` にすること
- 未決事項を残したまま確認を頼むこと

## 6. 確認を頼む
すべての仕様書を書き終えたら、次の内容を短く伝えて、一度だけ確認を頼む。
1. 読んでほしい仕様書の一覧（読む順に、リンクと一言の説明）。読むのは各仕様書の「👤 ユーザーが確認するところ」だけでよいこと
2. 実装前にユーザーが準備するもの（全仕様書の分をまとめる。なければ「ない」と書く）
3. 完成後にユーザーが手で確認するもの（全仕様書の分をまとめる。なければ「ない」と書く）
4. 「問題なければ OK と返信してください。OK をもらったら、すべての仕様書を最後まで実装します。直したいところがあれば、その内容を伝えてください」

修正の指示が返ってきたら、仕様書を直し、変えた部分だけを伝えて、もう一度確認を頼む。

## 7. 合意をもらったら、最後まで実装する
ユーザーが合意を伝えたら（「OK」「合意」「進めて」など）、追加の指示を待たずに次のことを行う。
1. すべての仕様書の状態を `合意済み` にし、`docs/specs/README.md` の一覧と、TASKS.md の決定事項ログ（合意した日付）に反映する。
2. CLAUDE.md の「進め方」に従い、依存の順に、すべての仕様書が `完了` になるまで実装する。仕様書が1つ終わるたびに、次に進んでよいかを確認しない。
3. すべて終わったら、最後の報告をする：作ったもの、検証の結果、実装中に「実装メモ」を直した点、ユーザーが手で確認する項目の一覧。
